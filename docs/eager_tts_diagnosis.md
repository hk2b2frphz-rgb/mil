# eager TTS の通信待ち調査 (2026-09-09)

## 確認できたこと

- 提供された PBS ログは `az_e_tts10k3`。4 shard を起動した後、
  `walltime 86499 exceeded limit 86400` で終了している。
- shard_002 の写真では Hugging Face の Qwen3-TTS CustomVoice への HEAD
  リクエストが繰り返し失敗している。音声生成の進捗は写真からは確認できない。
- 別の回答画面に引用された例外は `ProxyError` → `NameResolutionError` →
  `Failed to resolve 'rdproxy.intra.hitachi.co.jp'`。元ログ全文は未入手なので、
  この引用が正しければ、直接の通信障害は計算ノードでのプロキシ名のDNS解決失敗。
- 09-04版 eager / normal / reserved は、同じ `xvn_s` / `res=middle2`、
  clone参照、共通vLLM runnerを使う。専用のプロキシ設定はない。
  コーパス名と入出力先は異なるが、eager頻度で通信経路を変える分岐はない。
- 共通runnerは `setup_proxy.sh` を読み込み、shardは親環境を継承する。
  `enabled` は変数の設定完了を意味し、DNSや接続成功の証明ではない。

## コードで再現・確認した問題と対策

1. `PROXY_CONFIG_INITIALIZED=1` を `qsub -V` で継承すると、明示した新しい
   `PROXY_URL` が無視され、古い `https_proxy` が残る。ローカルで再現済み。
   初期化済みフラグによる早期returnを除き、設定を毎回適用するよう修正。
   この不具合が当該ジョブで実際に起きたかは、当時の環境がないため未確定。
2. mixed-roleのバッチ処理は例外を個別音声リクエストに分解して再試行する。
   遅延モデル読込もその内部だったため、初期モデル読込の通信障害まで
   リクエストごとに繰り返し得る。初期読込を例外分解の外に移し、
   失敗時はshardを終了する。音声データ固有の失敗の分離は維持する。
3. TTSの事前確認は主にimport/GPU検査で、Hub接続を確認していなかった。
   計算ノードで30秒上限の接続確認を追加。ノード名、キャッシュ設定、
   認証情報を除いたプロキシ表示をログに残し、DNS障害なら起動前に停止する。
   `HF_HUB_OFFLINE=1` ではHub確認を省略するが、必要ファイルが揃っている必要がある。

## 未確定の点

eagerだけで起きる理由は、成功したnormal/reservedとの実行ノード・投入時の
プロキシ環境・キャッシュ・サーバー側コードの比較が必要。
ローカルの修正はDNSを修復せず、正しい社内プロキシを推測して切り替えるものでもない。

サーバーに変更を反映した後、通常のeagerジョブを再投入すると、
親ログの `[tts-net]` に実行ノードと接続結果が出る。
同じ出力先で再開し、既存データを消す必要はない。

```bash
qsub -V scripts/2026-09-04/aizuchi_eager_tts_10000.pbs
```

失敗した場合は、親ログの `[tts-net]` と直後のエラーを確認する。
名前解決失敗なら、そのノードで利用可能なDNS/プロキシの設定が必要。
ログインノードでの接続成功だけでは計算ノードの確認にならない。
